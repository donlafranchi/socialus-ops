## What the system is, in the kit's terms

The method has no router in code. The routing is done by a person-shaped layer: Dispatch files asks and starts "lanes" (one Code session per product area per shift), the lanes build, a second session reviews, CI merges, scheduled tasks report twice a day. The agents are Claude Code sessions, skills and scheduled tasks; the glue is `DISPATCH.md` (shifts, lanes, modes, handoffs), `PIPELINE.md` § Build rules, the `handoff/` file and two of the five scheduled tasks. The inventory is `inventory.tsv` beside this file.

Observed traffic, 2026-10-13 to 2026-10-26: 188 merges in socialus-web (56 change, 49 chore, 38 bug, 18 docs, 13 daily seeds, 12 criterion reports), 46 under `human-review`, 65 under `review-skipped`; 191 merges in socialus-plan of which about 117 are the status and dashboard workflows regenerating themselves; 16 in socialus-ops of which 9 are the trial scoring layer, tend-docs and audits; 36 sessions, 30 of them socialus-web lanes; 5 scheduled tasks; 40 GitHub workflows (33 web, 4 plan, 2 ops, 1 skills); 33 skills (150 KB). No trace export exists, so chains come from the method docs and the session titles, and every traffic figure is inferred from git, GitHub and the session list.

## Prompt notes

What the fold step will need from each prompt.

- **Hard limits written as prose**: "never force-push", "never apply a migration", "no new paid service", "max 2 builds", "no personal names in a public repo", "no em dashes" (the last is already a lint). Each belongs in a check or a deny rule, not a paragraph. The kit's rule: a limit the model has to remember is a limit it can forget.
- **Persona lines**: "Act as the build/TDD agent", "Act as the ticket-writer agent", "Act as the architecture and design reviewer", "Act as the product-doc trimmer", "Dispatch only". One agent, one voice; delete.
- **Instructions about other agents**: "Dispatch starts the next shift's lanes", "Cowork reviews it in a comment", "send it back to the build agent", "Dispatch messages the PM", "Dispatch tells whichever agent is working to merge it". They encode the routing; most go with the glue.
- **Rules different sessions appended to the same file**: `PIPELINE.md` § Rulings holds 40 dated lines; the decision rule is copied into three files; beta and freeze dates differ across six files (grade § 1 rows 5 and 7). One copy each.
- **Older-model instructions**: the slackbot reply hooks re-prompt every turn; `build-ticket` and `verify-before-done` restate "run the tests before you say done" in several places. Run `/claude-api prompt-audit` over CLAUDE.md, DISPATCH.md, PIPELINE.md and the seven role skills in step 5.
- **What stays in the main prompt**: the decision rule and decision rights, the five kinds of work, who checks what, the absolutes by slug, WHERE-THINGS-GO. Under 1,500 words for Code (grade § 5).

## Evals

Filled in during step 1. What exists today, from the grade (2026-10-22) and this audit:

| Eval | What it measures | What to do with it |
| --- | --- | --- |
| CI on every PR: lint, types, build, unit, browser, migrations three ways, visibility matrix, action-layer and ontology conformance, markers | Whether the code is correct | Keep as the gate; it is not the main metric, because every variant must pass it |
| deploy-health, smoke-live, main-build-alarm | Whether production works after merge | Keep; a failure files an Issue, which is a task that notices a dropped handoff |
| The grade card's five computable numbers: PR open to merge (median), main red minutes, PM items older than 7 days, `found-by-pm` Issues per 10 merged PRs, words an agent must read per role | The factory, end to end | Candidate main metric; none is computed by a script yet |
| Trial scores (ci-health, gap-leakage, doc-drift) | The method's own health | Do not use; their tuning notes call most red scores false |
| The reviewer's GitHub review per UI PR | Rule violations caught before the PM | Count findings per PR as a quality signal; not a metric to maximise |

Main metric: **to settle with the PM in step 1.** The kit wants ten tasks run on each variant. A software factory cannot replay "build this feature" ten times per change at a sane cost, so the proposal is observational: for every merged PR in a window, (a) PM touches needed beyond the ask, (b) hours from Issue to merge, (c) pushes after the first CI run, (d) `found-by-pm` Issues per 10 merged PRs, (e) tokens an agent reads before the Issue; the baseline is the last 14 days and each change is read over the following week. This departs from the kit's A/B eval and says so.

Gaps noticed: `found-by-pm` has 0 data points (no PM look has been recorded); PM touches are not distinguishable from agent actions because every agent posts as the PM's GitHub identity; no trace of which skill fired in which session.

Chains with no task (inferred from the docs, no trace export): ask → Issue → lane → reviewer → merge → smoke-live → dashboard; scenario → review-draft-scenario → write-tickets → build-ticket. Neither chain has a task that grades its end today beyond CI being green.
